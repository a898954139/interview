USER MEETING / DISCOVERY

先把「要解的工作」問清楚

這次會議不是蒐集一串功能，而是把第一個可驗證的工作情境、資料責任、人的決策點與系統承接方式對齊。先取得可被驗證的答案，才進入欄位、介面與排程細節。

THE FOUR FRAMING QUESTIONS

用四個核心問題收斂對話

若這四題還沒有答案，就先不要把討論收斂成系統畫面或欄位規格。

01 / OUTCOME

流程要完成什麼？

從哪個 WBS／採購情境開始，什麼狀態才算真正完成、可交接或可付款？

02 / DATA

需要哪些資料？

資料現在在哪裡、誰建立與維護、哪些欄位是判斷或簽核的依據？

03 / DECISION

哪些地方需要人？

哪些判斷必須由人批准，哪些工作能由規則、AI 或自動流程協助？

04 / HANDOFF

哪個系統承接？

結果寫回何處、失敗如何處理、管理資料與 BI／AI 要如何取得回饋？

FACILITATOR GUIDE

會議中的追問順序

每一組問題都要把「誰說的、根據什麼、還差什麼」留下來。

1. 範圍與預期成果

先界定第一個可跑通的情境，不一次把所有工程、採購與財務流程包進來。

  • 第一個要驗證的 WBS package 是哪一個？記下：起訖事件、業務 owner、成功定義
  • 今天的痛點是資訊看不到、簽核太慢，還是資料重複輸入？記下：可量化的現況證據
  • 哪些案例刻意不放進第一階段？記下：排除原因與之後的處理條件

2. 流程、簽核與例外

確認流程不是只看順序；每一個決策點都要知道誰能放行、誰能退回。

  • 每個關卡的輸入、輸出與必簽角色是什麼？記下：核准、知會、代理與升級規則
  • 預算不足、供應商資料不全或驗收失敗時怎麼走？記下：例外路徑、SLA、處理 owner
  • 哪些規則可以自動檢查，哪些只能人工判斷？記下：規則條件與人工裁量理由

3. 資料與系統責任

把物件、欄位與系統所有權說清楚，避免 Demo 看似完整但沒有可落地的資料來源。

  • WBS、供應商、物料、資產與會計資訊各由誰主責？記下：系統 of record、建立／修改權限
  • 目前哪些資料仍在 Excel、Email 或紙本？記下：範例、頻率、資料品質問題
  • ERP、規劃系統與中介層之間誰發起、誰回寫？記下：事件、欄位、失敗復原方式

4. Pilot 與驗收證據

在會議結束前，定義小到可以驗證、又足以代表真實工作的 Pilot。

  • 誰提供真實但可控的測試案例與資料？記下：資料 owner、可用日期、去識別要求
  • 什麼證據表示流程比現在更好？記下：時效、錯誤率、追蹤性或人工工時
  • 誰有權確認 Pilot 可以往下一階段走？記下：驗收人、決策日期、未通過處理方式
QUESTION SET / USE IN THE MEETING

從範圍到驗收的訪談問題集

每一題都建議記錄：回答人、目前證據、待確認 owner、以及下一次要回來確認的日期。這樣才能把 meeting 對話變成可追蹤的 discovery 輸出。

01. 範圍與成果 04 Q
  1. 這次先要跑通哪一個建廠／採購情境？確認起點、終點、對應 WBS 與代表性案例。
  2. 誰會因為這個改變受益？目前花多少時間或承擔什麼風險？用具體角色、頻率與事件來描述，不只用「效率不好」。
  3. 流程完成後，誰拿到什麼可用結果？例如：可送審的 PR、可執行的 PO、可驗收的收貨、可付款的憑證。
  4. 第一階段有哪些情境明確不做？留下排除清單，防止 scope 在會議後失控。
02. 流程、簽核與例外 04 Q
  1. 每一關開始與結束時，誰負責、輸入是什麼、輸出是什麼？不要只記流程名稱；要能辨認實際 handoff。
  2. 誰能核准、退回、代理或升級處理？區分必簽、知會、授權與權限例外。
  3. 哪些錯誤最常出現？目前怎麼發現、怎麼補救？包含預算、供應商、交期、數量、品質與憑證不一致。
  4. 哪些判斷可以由規則或 AI 協助，哪些一定要人決策？把推薦、判斷、核准與最後寫回系統分開描述。
03. 物件與主資料 04 Q
  1. WBS、預算、供應商、物料、資產與會計分類各自的 source of truth 是哪裡？確認建立、修改、停用與查詢的責任者。
  2. 哪些必要欄位現在沒有、格式不一致或靠人工補？需要真實樣本，不能只根據欄位名稱判斷。
  3. 一筆資料如何對到後續 PR、PO、收貨、驗收與付款？先找跨系統能追蹤的關鍵識別碼。
  4. 哪些資料屬於敏感、受控或需要留存稽核軌跡？包含權限、附件、版本與歷程。
04. 系統與介面 04 Q
  1. 規劃系統、ERP、文件與中介層各自承接什麼責任？避免以「系統名稱」代替真正的資料與交易所有權。
  2. 資料是即時、排程、人工匯入，還是以事件觸發？釐清觸發者、頻率、重送與重複處理規則。
  3. 介面失敗時，誰先知道、誰修正、誰能重新送出？需要錯誤碼、通知、待辦與可追蹤的補償流程。
  4. 哪些既有 API、批次檔、表格或報表能作為起點？會後要拿到實際存取條件與技術 owner。
05. 控制、AI 與治理 04 Q
  1. 哪些規則是不可違反的控制點？例如預算可用性、核准層級、供應商資格、驗收與付款三方比對。
  2. AI 可以讀、比、提醒或建議到哪裡？明確界定不能自行批准、不能直接寫入正式帳的邊界。
  3. 誰確認 AI／規則的結果可被採用？需要資料 owner 與業務 owner 的責任分工。
  4. 管理資料與 BI 要看哪些指標來判斷流程變好？先定義指標、口徑、資料更新頻率與追蹤對象。
06. Pilot 與驗收 04 Q
  1. Pilot 的資料、角色與情境可以小到什麼程度？小到可控，但仍含有真實手續與一個例外。
  2. 誰提供資料、誰測、誰簽驗收？每個責任人都要有可承諾的日期。
  3. 驗收要看什麼證據，而不是「畫面看起來可以」？例如狀態可追溯、簽核留痕、錯誤可復原、資料可對帳。
  4. 若 Pilot 沒通過，是縮小範圍、補資料，還是調整流程？先約好 go／no-go 的決策方式與 escalation owner。
